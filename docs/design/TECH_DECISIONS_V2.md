# 技術選定・設計判断ログ

> 最終更新: 2026-08-31

## 1. この資料の目的

開発で使用している技術・サービスについて、単なる技術スタック一覧ではなく、**なぜ必要だったのか、どんな候補があったのか、なぜ採用したのか**という意思決定の過程を残す。

今後、新しい技術や外部サービスを導入するときも、原則として以下の流れで追記する。

**課題 → 要件 → 候補 → 比較 → 採用 → 採用理由 → 見直し条件**

## 3. Vue 3 / TypeScript / Vite / Pinia

### 解決したかったこと

Webアプリとして「どこいく？」を実装するためのフロントエンド基盤が必要だった。

### 採用

- Vue 3
- TypeScript
- Vite
- Pinia
- Vue Router

### Vue 3を採用した理由

開発者本人にVueの実務経験があり、**その経験を活かしてVueで開発したいという希望があったため**。

新しいフレームワークを学習すること自体を目的にせず、既に経験のあるVueを使うことで、「どこいく？」そのものの設計・実装に注力する方針とした。

### 各技術の役割

- **Vue 3**: UI・コンポーネントの構築
- **TypeScript**:
  Schedule、Response、移動条件などのデータを型付きで管理
- **Vite**: 開発サーバー・ビルド
- **Pinia**:
  認証状態、表示名、予定、参加者、回答などアプリ全体で利用する状態の管理
- **Vue Router**: 予定作成、回答、結果、招待URLなどの画面遷移

### 比較について

React等との詳細な比較表を作成して選定したわけではない。

今回は「Vueの経験があり、Vueで開発したい」という開発者自身の経験・希望を重視した選定。

### 見直し条件

現状は見直し予定なし。

Vueでは実現が難しい重要要件が発生した場合や、技術構成そのものを大きく変更する必要が生じた場合に再検討する。

## 4. Leaflet + OpenStreetMap

### 解決したかったこと

参加者が出発地点を地図上から指定できるようにする。

### 候補として考えたもの

- Leaflet + OpenStreetMap
- Google Maps系サービス

### 採用

**Leaflet + OpenStreetMap**

### 採用理由

Google Mapsにこだわる理由がなかったため。

今後Google Maps
Platformの他APIを積極的に利用する予定があるなら、地図もGoogleに統一するメリットが考えられた。

一方、現時点ではGoogleのAPI群へ統一する予定はなく、地図表示・地点選択という目的のためだけにGoogleへ寄せる必要性は低いと判断した。

そのため、既存のWebアプリへ組み込みやすく、OpenStreetMapの地図データと組み合わせられるLeafletを採用した。

### 現在実装できていること

地図上の地点をクリックすると、

1.  マーカーを表示
2.  緯度・経度を取得
3.  Supabaseへ保存
4.  再アクセス時に地点を復元

できる。

### 現在の状態

Geoapify の Forward Geocoding / Reverse Geocoding を実装済み。徒歩・車の回答では、地名入力から緯度経度を取得し、地図上の地点選択から住所・地名を取得できる。出発地点文字列と緯度・経度を responses に保存し、再表示に利用する。

### 見直し条件

Google Maps
Platformなど、特定の地図プラットフォームへ統一する明確なメリットが生じた場合に再検討する。

## 5. Geoapify

### 解決したかったこと

Leafletの地図上で出発地点をクリックすると緯度・経度は取得できるが、「上野駅」「東京都港区...」などの地名・住所は別途入力する必要があった。

地図を単なる座標取得UIではなく、**出発地点を指定するためのUIとして成立させる**必要がある。

### 必要な機能

まず必要なのはReverse Geocoding。

```text
地図クリック
↓
緯度・経度を取得
↓
Reverse Geocoding API
↓
住所・地名を取得
↓
出発地点へ自動反映
```

現在は通常のGeocodingも実装し、

```text
「上野駅」と入力
↓
候補を選択
↓
緯度・経度を取得
↓
地図へマーカーを表示
```

という双方向の入力を利用している。

### 比較候補

- Geoapify
- LocationIQ
- Mapbox
- Google Maps Platform
- OpenStreetMap Nominatim

### 比較で最も重視した条件

**料金。**

個人開発・MVPであるため、まず無料または低コストで運用できることを最優先した。

そのうえで、

- Reverse Geocodingを利用できること
- Leafletとの相性
- 取得結果をアプリ側で扱いやすいこと
- 将来的にGeocodingへ拡張できること
- 本番公開後も運用しやすいこと

を考慮した。

### 比較結果の要点

#### Geoapify

- 無料枠が大きく、MVP段階では十分な余裕がある
- Leafletとの組み合わせがしやすい
- Reverse GeocodingとGeocodingの両方へ拡張できる
- 今回のデータ保存・再表示の設計と相性が良い

#### LocationIQ

- 無料リクエスト数の面では非常に有力
- 料金だけを見ると強い候補
- 総合的な扱いやすさや現在の構成との相性を含め、今回はGeoapifyを優先

#### Mapbox

- 無料枠は魅力的
- Geocoding結果の保存条件が今回のSupabaseへの保存・再表示設計と噛み合いにくい

#### Google Maps Platform

- 高機能でエコシステムも大きい
- 今回は料金を最優先している
- 他のGoogle Maps Platform
  APIへ統一する予定も現時点ではないため、積極的に選ぶ理由が弱い

#### OpenStreetMap Nominatim 公開API

- 無料
- 公開APIには利用ポリシーやリクエスト頻度等の制約がある
- 一般公開するアプリの本番APIとして積極的に依存するより、専用サービスを利用する方針とした

### 採用

**Geoapify**

### 採用理由

料金を最優先しつつ、

- 無料枠
- Leafletとの相性
- Reverse Geocoding
- 将来のGeocodingへの拡張性
- Supabaseへ回答を保存・再表示する現在の設計との相性

を総合して採用。

### 決定日

2026-08-28

### 見直し条件

- 無料枠を継続的に超える規模になった場合
- 日本語の地名・住所精度に問題が見つかった場合
- LocationIQ等の他サービスに大きな料金・機能上の優位性が生じた場合
- 地図サービス全体を別プラットフォームへ統一することになった場合

## 10. 技術選定で大切にすること

「有名だから」「おすすめされたから」だけでは採用理由にしない。

「どこいく？」に必要な機能、個人開発としてのコスト、開発者自身の経験、既存構成との相性を踏まえて選択する。

また、当時の比較記録が残っていない技術について、後からもっともらしい理由を作らない。

必要であれば現在の要件で再評価し、

**「当時の詳細な選定理由は未記録だが、現在あらためて比較した結果、○○の理由で継続する」**

という形で意思決定を更新していく。

## 11. 予定単位の移動方針（transport_policy）

### 解決したかったこと

回答者ごとに電車を選ぶ方式では、予定そのものが「電車で行く予定」なのか、「各自が徒歩・車・条件なしを選ぶ予定」なのかを表現できなかった。

### 採用

`schedules.transport_policy` を追加し、次の2値で管理する。

- `transit`: 電車固定
- `flexible`: 各自で徒歩・車・条件なしから回答

### DB / UI整合

- `transit` では回答の `transport_mode='transit'`、出発地点・緯度経度・移動時間は NULL、`preferred_areas` は1〜5票。
- `flexible` では `walking` / `driving` / `null` を利用し、電車は回答UIに出さない。
- 徒歩・車は出発地点・緯度経度・移動時間を必須とする。

### 採用理由

予定全体の前提と個人の回答を分離でき、回答0件の時点でも交通方針を確定できるため。booleanではなく文字列Unionとし、将来の方針追加にも対応しやすくした。

### 決定日

2026-08-29

### 見直し条件

- 交通方針が3種類以上へ増える場合
- 電車でも出発地点・所要時間を回答する仕様へ変更する場合
- Routing / Isochroneを本格導入する場合

## 12. 簡易移動範囲の表示

### 解決したかったこと

徒歩・車の出発地点と移動時間を、集計結果で直感的に確認できるようにする。

### 採用

Leaflet の `L.circle()` を使った表示専用 `TravelRangeMap` と、純粋関数 `calculateTravelRadiusMeters()` を利用する。

- 徒歩: 1分 = 100m
- 車: 1分 = 500m

### 採用理由

MVPではRouting APIを追加せず、既存の緯度経度・移動時間だけで軽量に「おおよその範囲」を可視化できるため。

### 表現上の制約

これは直線距離の概算であり、道路ネットワークや実際の所要時間を保証しない。複数円の重なりも「全員が行ける範囲」「最適エリア」を意味しない。transitと条件なしは表示対象外。

### 見直し条件

候補地推薦や到達可能範囲の精度がプロダクト価値の中心になった場合は、Routing / Isochrone APIを再検討する。

## 13. Home と予定一覧の責務分離

### 課題

Homeと予定一覧が同じ予定情報とCTAを多く持ち、画面の役割が曖昧になっていた。

### 採用

- Home: 「今の自分に必要な行動を見る」
- 予定一覧: 「参加しているactive予定を状態別に探す」

Homeは未回答 / 回答待ち / 全員回答済みの各状態から代表1件だけを表示。予定一覧は3状態に分類し、各セクションを横スクロールにする。ScheduleCardは予定名 / 日程 / 回答進捗 / 自分の状態 / chevronの5要素だけとし、全カードを予定詳細へのRouterLinkへ統一した。

### 採用理由

Homeをアクション中心、予定一覧をナビゲーション中心に分けることで、同じ予定データを扱いながら画面の目的を明確にできるため。

### 決定日

2026-08-31

## 14. 非同期状態と送信中UI

### 課題

通信中・失敗・0件・Not Foundが同じ見え方になると、ユーザーが現在状態を判断できず、二重送信も起こり得る。

### 採用

予定データに `idle / loading / success / error` を持たせ、Loading / Error / Empty / Not Found / Content を分離する。BaseButtonにはloading状態を持たせ、予定作成・回答保存では二重送信を防止する。

回答保存後は再取得し、Store上でcurrent userのresponseが確認できた場合のみ予定詳細へ遷移する。

### 採用理由

通信失敗を「空データ」と誤認しないこと、保存成功前に画面遷移しないこと、操作中のフィードバックを統一することを重視した。

## 15. 現在保留している候補推薦機能

候補地・店舗の自動推薦は現時点で未実装。現在のResult上部は、日付・活動・希望エリアの3軸をそれぞれ独立集計した代表値であり、組み合わせ最適化ではない。
